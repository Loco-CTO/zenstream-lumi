# Release process

## Version and package contract

The package version in `pyproject.toml` is authoritative. Stable release tags use `vMAJOR.MINOR.PATCH` and must match that version. The release workflow publishes a runtime archive and host-specific dependency wheels with recorded SHA-256 values; it never includes Qwen checkpoints or model weights.

The Lumi runtime is installed and imported by a compatible Orchestrator release. It is not a separately deployed service. Preserve the runtime API compatibility fields and the Orchestrator allowlist contract when preparing a release.

## Native runtime matrix

The validated release targets are Windows x64 and Linux x64 with CPU, CUDA, and Vulkan backends, and Linux ARM64 with CPU only. The CPU backend remains available as fallback. Do not claim HIP/ROCm or Metal support without a supported, tested release target.

Native build IDs in `pyproject.toml` bind wheel reuse to the llama.cpp source, toolchain, SDK pins, backend flags, architecture, and platform baseline. Bump the affected ID when any of those inputs change. Release scripts verify wheel hashes and backend contents and smoke-test supported Python ABIs before publishing.

## Release checks

- Run `python -m unittest discover -s tests -v` and `ruff check lumi tests scripts`.
- Run `python -m unittest discover -s tests -p 'test_release_build.py' -v` for archive behavior.
- Review `scripts/build_release.py`, the release workflow, and `pyproject.toml` together; do not hand-edit release manifests generated by those scripts.
- Keep model data, local runtime output, and benchmark files outside the release archive and repository.
