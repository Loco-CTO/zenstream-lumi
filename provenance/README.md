# Lumi provenance records

The [synthetic output terms audit](GENERATOR_TERMS_AUDIT.md) records why the separate 101-case OpenAI/Codex-generated draft inventory remains ineligible for human review, scoring, and training until its historical account terms and Lumi use/distribution scope are established.

The public repository contains provenance formats and research documentation, not training text or evaluation case text. `data_sources.json` is the collection-level catalog of external, authored, or synthetic sources. It records one narrowly scoped ASDC item approved for a public Japanese development diagnostic; its raw text and sample-level record remain in controlled local storage. The separate 101-case assistant-generated draft source and its item records remain unresolved and unusable until their applicable service terms and use scope are reviewed; aggregate status is in the [metadata-only draft inventory manifest](../evaluation/draft_inventory_manifest.json).

`document_records.schema.json` defines one JSON object per released, processed, or authored sample. Store records as newline-delimited JSON in a controlled data-build artifact, with one line per exact sample made available to training, tokenizer learning, generation, or evaluation. Do not add source text to the public repository. For each record, retain stable source item IDs, source and revision URLs where available, hashes of source and resulting text, rights evidence, permitted uses, attribution, transformations, split, privacy review, and upstream record IDs. A mixed document assembled from multiple inputs must list every parent source record.

Each training run must pin the source manifest, document-record artifact, transformation code/configuration, tokenizer inputs, and split manifests by revision and SHA-256. Keep development and final holdout records outside training, filtering, synthetic generation, and tokenizer input. When rights or privacy terms prohibit exposing an item-level ledger, retain the full ledger in controlled storage and publish its immutable hash plus a safe summary.

Manually authored material also requires an entry in the metadata-only `author_consents.json` manifest and `author_consents.schema.json` schema. The validator joins its opaque consent ID to the exact pseudonymous author, manually authored source, item ID, and sample SHA-256; approved uses must be covered by the grant, including through every derived sample's parent lineage. A training use also requires explicit permission for model artifact distribution. Keep any non-empty consent manifest, agreements, names, contact details, signatures, and author-to-pseudonym mapping in controlled storage outside the repository. The manifest's agreement hash and approval metadata are references for a human rights review; they do not prove that an agreement is genuine or legally sufficient. The file validator rejects a non-empty consent manifest located inside a Git worktree.

No sample-level records are committed. The controlled local ASDC diagnostic bundle contains the single admitted item-level record matching the exact upstream sample hash in `data_sources.json`. The separate local 101-case assistant-generated draft evaluation bundle has matching case and sample hashes, but all records remain review_pending, with unknown rights, unchecked contamination, and unreviewed privacy. It is not an approved source and must not be shown to human reviewers, scored, or used for training. The blind review workbench and ledger importer both validate the full source, generation, and sample-record bundle before allowing review data to be collected or joined.

Before collecting new author-written cases or training examples, follow the [human contributor intake checklist](AUTHOR_CONTRIBUTION_CHECKLIST.md). It is an operational checklist, not a consent agreement or legal determination. Record training uses and model artifact distribution only when the reviewed grant covers the exact intended scope; evaluation-only permission must not be reused for training.

## Provenance gate

Run the standard-library validation gate before building a dataset, exposing evaluation cases for human review, importing review ledgers, or scoring an evaluation set:

```powershell
python provenance/validate.py --records <document-records.jsonl>
python provenance/validate.py --records <document-records.jsonl> --cases <evaluation-cases.jsonl>
```

The gate checks unique record IDs, source and generation references, source revisions, intended-use declarations, sample-level rights and review status, synthetic prompt/model provenance, author consent joins, split consistency, parent lineage, and evaluation case hashes. An approved evaluation item requires `evaluation_use: permitted` in both its source record and its item-level rights record. Training inputs separately require `training_use: permitted`; manually authored training samples additionally require a matching approved grant that explicitly allows model artifact distribution. Conditional or unknown permission is not enough for the automated gate to pass an approved record. Pass `--author-consents <controlled-manifest.json>` when using a non-empty controlled manifest; the default tracked manifest intentionally contains no grants.

Evaluation schema v4 records map `development` cases to the `development` provenance split and `final_holdout` cases to `sealed_holdout`. Each case record's sample hash is SHA-256 over canonical UTF-8 JSON containing its schema version, case and family IDs, split, language, categories, conversation turns, trusted context (including its complete inline fixture or `null`), the full fixture-only `tool_scenario` or `null`, and gold intent, response contract, presentation intent, and expected ordered tool trajectory when present. Case-level review references and provenance metadata are excluded from that hash. The controlled review ledger binds every case-label decision to the same sample hash, avoiding a hash cycle while detecting edits to reviewed content. Editing any evaluation content therefore requires updating its sample-level provenance hash and repeating the affected reviews.

The gate verifies declared metadata and joins; it does not determine whether a license interpretation is legally correct, validate that an arbitrary training artifact's bytes match its declared hash, or replace native-language and subject-matter review. Keep the actual data-build artifacts and source evidence in controlled storage, and preserve their hashes with each run.
